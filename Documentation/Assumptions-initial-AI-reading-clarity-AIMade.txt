Internal Request System — Consolidated Assumptions

Reading guide

Use this brief as the working summary. If wording differs across versions, use Assumptions-initial-HumanMade.txt as the source of record. The complete text of each source file appears in the appendix.

1. Project scope and audiences

Build a company-internal request system that can serve as the backend for HR ticketing, organization-wide bug reporting and handling, and other internal request workflows that require approval.

Produce two editions of each of the following artifacts, optimized for AI readers and human readers respectively.

- Assumptions
- High-level design (HLD)
- Low-level design (LLD)

2. Decision approval

Ask the project owner for approval before making any important decision during conceptual work, high-level design, low-level design, or development planning.

3. Delivery phases

1. Conceptual work. Identify all features and quality acceptance criteria and describe them in separate Markdown (.md) files. Define domain entities and their relationships at the conceptual level. Keep the domain divided into small entities and maximize long-term maintainability and extensibility.
2. High-level design. Put the main Markdown HLD in its own directory. Link from it to supporting documents in the repository and structure them so their contents can be incorporated into a complete HLD at any time. Keep each document relatively short, preferably under 5,000 characters. Longer documents are acceptable when justified.
3. Low-level design. Put the main Markdown LLD in its own directory. Link from it to supporting documents in the repository and structure them so their contents can be incorporated into a complete LLD at any time. Keep each document relatively short, preferably under 5,000 characters. Longer documents are acceptable when justified.
4. Development planning. Create a detailed application development plan broken into small tasks.
5. Development. Use test-driven development (TDD).
6. Iterative improvement. Review the work and identify justified changes. Update the conceptual documents and then the design documents when needed. Update the planning documents with a new version entry, then implement the changes. Record version information in commits and keep endpoints unversioned.

4. Conceptual assumptions and work

- Use Java 25 and Spring Framework 7.0.11.
- Expect many new requirements after the system enters production. Design the system to accommodate those changes.
- Expect high load and multiple application instances running concurrently. Treat 100 requests per second as a measurable capacity requirement. Ensure idempotency at the database level.
- Assume the organization has user types, roles, and groups. For example, certain roles or groups can approve particular requests.
- Assume the corporate environment uses Workday, Atlassian Jira, ShiftLeft, SonarQube, Sonatype, and other common enterprise tools. Assess the business value of each integration and make ease of integration an acceptance criterion.
- Prefer base interfaces with implementation classes that can be extended to meet the needs of a particular integration, business use case, or application. In that approach, define core functionality and lifecycle behavior in the base classes.
- List the types of real production issues that occur in similar applications and design the system to withstand them.
- Optimize for varied use cases. Evaluate whether the base functionality should be a dependency of implementations for specific business cases.

5. High-level design priorities

- Address idempotency, concurrency control, and reliable integration delivery.
- Prioritize clarity and maintainability.

6. Low-level design preferences and evaluations

Prefer Spring's existing configuration and classes. A dependency is an option when its advantages are justified. Describe those advantages in the LLD edition for AI readers.

Evaluate each of these seven options against the project goals.

1. Generate data transfer objects (DTOs) from YAML files.
2. Generate DTO mappers at compile time.
3. Detect breaking API changes in continuous integration (CI).
4. Generate types from the database schema.
5. Generate event payloads from schemas.
6. Enforce package boundaries with tests.
7. Make retries safe and test them against PostgreSQL.

7. Quality measures

- Follow Spring Security Advisories and the Snyk Vulnerability Database for security handling.
  Spring Security Advisories — https://www.google.com/goto?url=CAESVwHEIkXX09d4tmaAdkFjJfVnizibDzCZ5ZFv1iuFCTqimQum_q8vKZKDP_1n29M5RAF-TbaVtLSOA2AG2JwsQXBuXeErULX1DALS0wJzJVOxklvtpTXgwg
  Snyk Vulnerability Database — https://www.google.com/goto?url=CAESYAHEIkXXPiJDD1pdnZTtAVbKQ3CTBZ0Wb2jZdkg7urIy_hcAyUoELhGJCkRcXcxqPkyxy1sbmLJXe5BkbztYjHtwGDYkVSryqEYTEk5YWd9nnVw1atMAErdE5QUfLgMLuA
- Complete every request in under 3 seconds. Aim for substantially lower latency for most requests.
- Keep cyclomatic complexity consistently low.
- Log every error with a descriptive, understandable message.
- Log every incoming and outgoing request.
- Validate requests thoroughly and early. If the database rejects certain characters, check for them in the controller.
- Include additional quality measures as they are identified.

Project scope

The system will provide a shared backend for requests within the company. It should support HR tickets, bug reports and their resolution across the organization, and other internal processes that depend on approval. The assumptions, high-level design (HLD), and low-level design (LLD) each need two editions tailored to how an AI or a person will read them.

How the work will proceed

1. Establish the concept. Capture the feature set and quality acceptance criteria in separate .md files. Sketch the domain by identifying small entities and describing how they relate. Shape the model for long-term maintenance and extension.
2. Draft the HLD. Give it a directory of its own and use Markdown for the main document. Link to supporting documents in the repository so their text can be inserted into the main file to assemble the full design at any time. Keep individual documents relatively short, preferably below 5,000 characters, with longer documents allowed when there is a reason.
3. Draft the LLD. Use a separate directory and a main Markdown file with links to the supporting documents in the repository. Structure those documents so they can be incorporated into a complete LLD at any time. Apply the same preferred length of under 5,000 characters per document, with room for justified exceptions.
4. Plan implementation. Break the development work into detailed, manageable tasks.
5. Implement the plan through test-driven development.
6. Repeat the review and improvement cycle. Use each review to determine which changes are warranted. Revise the concept and then the design documents if the changes call for it. Add a new version entry to the planning documents before implementing the revised plan. Track version information in commits and leave endpoints unversioned.

Ask me to approve every important decision during conceptual work, high-level design, low-level design, and development planning.

Constraints that shape the concept

- The implementation will use Java 25 and Spring Framework 7.0.11. Expect many new requirements after launch and design the system so it can absorb them.
- Design for concurrent operation across multiple application instances. Use 100 requests per second as a measurable capacity requirement and guarantee idempotency at the database level.
- Assume the organization already has user types, roles, and groups. Some roles or groups will have permission to approve particular requests.
- Anticipate a workplace that uses Workday, Atlassian Jira, ShiftLeft, SonarQube, Sonatype, and other common enterprise software. Evaluate the business benefit of integrating with each tool and use ease of integration as an acceptance criterion. Favor base interfaces and implementation classes that can be extended for a particular integration, use case, or application. Put the common functionality and lifecycle behavior in the base classes.
- Identify the kinds of production failures seen in comparable applications and design to withstand them. Support different business workflows and consider making the common functionality a dependency that each use-case-specific implementation can build on.

What the design needs to cover

The HLD should explain how the system enforces idempotency, controls concurrent activity, and ensures reliable delivery to integrations. Keep the design clear and maintainable.

In the LLD, start with the configuration and classes Spring already provides. Bring in an additional dependency when its benefit justifies it, and explain that benefit in the LLD edition for AI readers. Evaluate the fit of the following options for this project.

- YAML-based DTO generation and compile-time generation of DTO mappers.
- CI checks for breaking API changes.
- Type generation from the database schema and event payload generation from schemas.
- Automated tests that enforce package boundaries.
- Safe retries and tests that verify retry behavior against PostgreSQL.
