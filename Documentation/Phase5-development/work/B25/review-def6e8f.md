## Blocking finding

The slot-availability query in `JdbcDispatchScheduling` (lines 44–49) counts only unexpired `CLAIMED` and `ARMED` attempts. It uses a PostgreSQL advisory lock for the remaining occupancy check. The durable attempt records retain the slot number, but there is no field recording that the connector invocation is still outstanding. An armed expiry moves the attempt to `UNKNOWN` (lines 472–490 of `JdbcDispatchStore`). A connector deadline can also produce `UNKNOWN` before lease expiry. [Slot query and session lock](../../../../tmp/phase5-development/b25-independent/exact/adapter-integration-jdbc/src/main/java/com/company/requests/adapter/integration/jdbc/JdbcDispatchScheduling.java) · [Scheduling migration](../../../../tmp/phase5-development/b25-independent/exact/adapter-integration-jdbc/src/main/resources/db/integration/outbox_scheduling_v1.sql) · [Attempt transitions](../../../../tmp/phase5-development/b25-independent/exact/adapter-integration-jdbc/src/main/java/com/company/requests/adapter/integration/jdbc/JdbcDispatchStore.java)

The connector runs on a separate thread using a separate data source. After the two-second deadline, the worker interrupts the call and waits for its thread to exit. PostgreSQL releases the session advisory lock as soon as the workflow backend ends. If both destination slots have live calls and one loses its backend after expiry or transition to `UNKNOWN`, another worker can allocate that slot to an eligible sibling. All three calls may then overlap. The original effect can remain correctly held as unknown throughout. This finding follows from the candidate code and the bundled PostgreSQL semantics. [Timed invocation](../../../../tmp/phase5-development/b25-independent/exact/integration/src/main/java/com/company/requests/integration/TimedSyntheticDelivery.java) · [Scheduled composition](../../../../tmp/phase5-development/b25-independent/exact/bootstrap/src/main/java/com/company/requests/bootstrap/SyntheticDispatchConfiguration.java) · [PostgreSQL 18.7 advisory locks](../../../../tmp/phase5-development/b04-fixture/runtime/pgsql/doc/src/sgml/html/explicit-locking.html#ADVISORY-LOCKS)

For acceptance, shared storage must retain occupancy for an armed, outstanding invocation across the loss of its workflow session. Release must follow evidence that the invocation ended or can no longer arrive. Preserve independent destination progress and bounded resumption when capacity is genuinely available. The next review should establish the ceiling across that transition and distinguish unresolved delivery outcome from completed connector execution.
