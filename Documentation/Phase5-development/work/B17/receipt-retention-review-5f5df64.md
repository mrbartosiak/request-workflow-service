## Migration and proof

The owner entry point requires versions 1 and 2, takes the existing transaction-scoped migration lock, installs v3 and records it in one transaction. The version check makes reapplication idempotent. Both replacement triggers precede removal of the single foreign key selected by its source and target relations and ordered column lists. The request foreign key and deferred receipt finalization constraint survive. Existing witnesses keep their tuple versions. I compared the original live proof with the replacement. Both require the same request and final Publish fact, resulting state and revision, namespace and ID, scoped receipt key, action, ref, generation and original status. The request, final fact and live receipt must share the witness tuple's `xmin`, and the low 32 bits of the stored full transaction must match that tuple version. The replacement also checks the generated finalization flag. On append the immediate trigger requires the current full transaction and its matching receipt tuple. The command still checks the original namespace gate, exclusive organization guard and full finalized receipt on its bound connection.
