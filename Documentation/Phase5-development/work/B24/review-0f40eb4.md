## Blocking finding

**B24-R1. A claim that expires before arm prevents a later terminal response from settling the delivery.** The worker allocates an attempt number when claiming. Consider an `UNSAFE` route on which claim 1 expires before arm. Recovery records `EXPIRED_UNSENT`, and the original token can no longer arm. Claim 2 arms, reaches the endpoint and receives an authoritative throttle. The two local rows establish one possible send. The remote ledger has one terminal no-apply row for attempt 2 and zero effects. The accepted state for this transient is `RETRYABLE`. In `JdbcSyntheticConnector.closedPrefix` (lines 249–255), the count is 1 and the required unfenced prefix length is 2. The connector returns exclusion `NONE`. The delivery policy then records `UNKNOWN`; operator retry from the same authoritative ledger yields `QUARANTINED`. For a permanent rejection at attempt 2, the corresponding first disposition is also `QUARANTINED` instead of `FAILED_PERMANENT`. An earlier pre-arm `DEFERRED` row has the same effect. This is a deterministic source finding. The committed native throttle and permanent tests each start at attempt 1. The consequence is that safe progress stops, with zero remote effects.
