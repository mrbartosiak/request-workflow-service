## Blocking findings

**B29-R1 · Enforce recovery at the actual protected response handoff.** The recovery composition wraps the command data source. The registered Create route still passes status, a protected `Location` and body directly to Spring MVC. The fixture reads the completed HTTP response at `B08MvcSession.invoke`, copies its body and passes those bytes to a separate callback that only increments a counter. Its contention case holds that callback on a one-byte sample. The shared lock serializes this callback with containment, but a route that completed preparation before containment can still publish the original response after containment. Install the gate at the bounded handoff used by the recovery-enabled route. Exercise both orderings against the actual receiver. If containment wins, the receiver must see zero protected status, headers or body from the held success. If handoff wins, containment must wait until the bounded transfer completes. **B29-R2 · Start the restored database with private login rules.** The fixture copies the verified backup, changes its port and starts it with the original authentication rules and database grants. The first B29 check on the restored command data source opens a real connection before the application detects the mismatched lineage. The subsequent database `REVOKE CONNECT` closes new connections. A session admitted before revocation retains its existing workflow rights. Limit the B29 copy to the designated private roles before its postmaster starts. Verify raw command and both worker logins are denied on first availability and through certification, while the private verifier can still inspect the copy.
