# B22 handoff for dispatch and PostgreSQL verification

The synthetic effective-access profile accepts an optional Publish trigger for one request type and destination. The existing settings constructors leave it disabled. The configured type uses the regular guarded Publish route. Inside the owned command transaction, after the receipt, transition, publication witness and any scope change have been written, the application appends through `OutboxAppendPort`. The JDBC appender verifies the bound command data source, original Publish gate, exclusive organization guard, tenant, request reference, result revision and stable effect identity.

`JdbcOutboxMigration.migrate()` installs the workflow owner's add-on. Give the command role `INSERT` on `destination`, `tenant`, `effect_id`, `trigger_slot`, `request_ref`, `request_revision`, `operation`, `schema_version`, `projection_ref`, `scheduled_epoch_second` and `scheduled_nano`. PostgreSQL supplies the `READY` status. The primary key is `(destination, tenant, effect_id)`, and the scoped request, revision and trigger slot are constrained. A duplicate insert fails the original transaction. An exact command replay reads the protected receipt and leaves the original outbox row intact even if the trigger configuration changes.

The Publish slot is `publish.reference`. `effect_id` is lowercase SHA-256 of the US-ASCII bytes of `requests.outbound.effect.v1`, a line feed, the existing lowercase `PublicationJournal.receiptIdentity` digest, a line feed and the trigger slot. The receipt digest binds the exact issuer, organization, principal and token identifier. Changing a reservation or envelope version preserves the effect identity. A destination is a separate part of the primary key, with a tenant scope on every persisted effect.

The current application envelope is version 2 with projection reference `published-request-reference`. Retained version 1 uses `publish-request` with the same slot and coordinates. The typed `OutboundObligation` constructor validates both versions, and the SQL projection constraint matches the same allowlist. Both formats contain only the request and effect coordinates plus the exact second-and-nanosecond schedule. The projection carries no captured request material or publication ID. Workers resolve currently permitted data from the reference under their own guarded proof checks.

B23 should claim on its worker transaction and connection, preserve the full key in claim and attempt lookups, and apply `CurrentAccess.confirmedPublication` with current authority, destination permissions and cancellation checks before arming. B23 owns worker status transitions and scheduling indexes, attempt rows and all connector I/O. B34 can use the private `B22Postgresql` oracle and its post-insert fault for the same-connection P3 cut.
