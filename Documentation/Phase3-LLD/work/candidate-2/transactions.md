# Transactions and concurrent commands

**Scope** A-04, F-01–06/09, Q-02/03/11/13, R-01/02/08, DEC-03/04/08/13. **Status** Atomic effects are required. Lock-based reference implementation is proposed. [HLD consistency](../../../Phase2-HLD/local-consistency.md)

`CommandService` owns one business transaction per attempt on the shared writer. Acquire in order: writer-generation admission, applicable organization gate (declare shared/exclusive before locking), scoped operation key, target request(s) by stable ref, material facts by kind, then global creation/publication serialization row where applicable. Each authority writer uses the same compatible lock order. Mutations, cancellations and retention that change security-visible inputs use an exclusive scope gate. Per-command bounded timeout caps time in lock waits, database statements and external publication allocation. Never upgrade the scope lock in the transaction. [Access](access.md) · [IDs](identifiers.md)

1. Authenticate/validate upstream. Under the writer and scope gates check authority readiness and submitted action, scope and applicable target visibility. Apply retry precedence: expired key uses no receipt lookup; old-generation key resolves read-only; eligible current key uses unique-key arbitration. A permitted replay skips new-action workflow. [Retry precedence](retries.md)
2. For a new key, check key freshness/generation and authoritative target/scope visibility. Lock current request and facts for existing action. Recheck effect authorization, context visibility and token action, target, revision and all fact versions. Invoke workflow and type checks. Self-Accept check uses durable origin person.
3. Apply state/body, advance revision and append history only on state change. Store reason, receipt, required evidence and eligible obligations atomically. Prepare authority deltas and reserve IDs before local effects, in that order when both apply. Commit their witnesses with local effects. Create's provisional ref stays inside its transaction. Hold creation/publication lock through resolution. [Publication](publication-reconciliation.md) · [Authority](authority-recovery.md)
4. Known rollback clears local effects and closes journal attempts using affirmative proof; burnt IDs stay burnt. Release success after known durable commit, any required outside confirmation and fresh authorization. Use authoritative same-key resolution for uncertainty. Vendor sends run in dispatch. [Retries](retries.md) · [Outbound](delivery.md)

**PostgreSQL candidate** READ COMMITTED, `FOR SHARE` / `FOR UPDATE` on scope gates, and `FOR UPDATE` on request and serialization rows. Require known durable local commit with the datastore durability settings verified. Receipt claim uses unique-key `INSERT … ON CONFLICT DO NOTHING`. When it does not insert, read the receipt in a subsequent statement with a fresh statement snapshot. If the competitor rolls back, an admitted contender can claim and must check current authorization and eligibility. Treat canceled statement errors as transaction failures. Open a fresh transaction for resolution. [Explicit locks](https://www.postgresql.org/docs/18/explicit-locking.html) · [Isolation](https://www.postgresql.org/docs/18/transaction-iso.html) · [Insert](https://www.postgresql.org/docs/18/sql-insert.html)

| Same starting facts, distinct keys | Outcome |
| --- | --- |
| Publish vs Reject at ACCEPTED | First effect wins. Other stale or illegal under fresh context. One transition, ID only on Publish. |
| Edit vs Accept at VERIFIED | One wins against same starting revision. Re-observed Accept can follow Edit. Accept first closes editing. |
| Verify vs Delete at CREATED; Edit vs Edit | First wins. Other stale, or ineligible from a new observation. |
| Publish on distinct accepted requests | Both can succeed. Namespace lock orders assignments and durable publication commits. |

Conditional writes could reduce waits via guarded update on revision and all material dependencies. Prove the predicate covers policy/fact races and that losing writes cannot commit any ancillary effect. Event-sourced state offers replay evolution at projection/security cost. Prefer straightforward transactional rows for Phase 5 if approved. The production engine must independently prove durability, key arbitration, authorization ordering, transactional changes and restore fencing. [PostgreSQL evidence](postgresql-evidence.md)
