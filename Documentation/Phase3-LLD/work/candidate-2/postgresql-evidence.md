# Deterministic PostgreSQL retry evidence

**Scope** Q-02/03/10/13, R-01/02/08/10, DEC-03/04/07/08/13. **Status** Proposed planned evidence on real PostgreSQL. Production engine deferred. [Transactions](transactions.md) · [Retries](retries.md)

Use a pinned supported PostgreSQL release, exact migrations, two independent HTTP service processes sharing the writer, transaction barriers at named steps, scoped fixture actors and a controlled clock. Capture service/backend PID, database version, isolation and durability settings. Use actual inspected locks/blocked sessions when contention is the condition. Use barriers, not sleeps. Inject faults above the real JDBC transaction and at transport boundaries. Use a separate observer connection after each final outcome. Log only safe fixture IDs and record independent external authority results.

| Fixture and interleaving | Expected client and durable state |
| --- | --- |
| A claims key, B submits same intent. Release A to commit. Repeat with changed intent and then distinct keys for identical Create bodies. | A and B exact result with one ref on match. Authorized different intent returns KEY_CONFLICT and creates nothing. Independent keys create two refs. Check exact receipt/history/effect row counts. |
| A claims key and pauses past B's lock wait. Repeat with A forced to roll back after staged effects, before commit. | B first gets OUTCOME_PENDING and same-key retry resolves. In rollback variant B can acquire after current checks, completing one request, receipt and history, with no staged A effects. |
| A/B use distinct keys and same observed revision for Publish/Reject, Edit/Accept, Verify/Delete, Edit/Edit. Run both winner orders. | Winner alone increments revision and applies its state/history rule; loser stale with zero effects. Fresh observation can admit Accept after Edit. One ID/outbox if and only if fixture Publish wins. |
| A locks namespace, reserves n, pauses before commit. B publishes distinct request. Repeat with A aborting after reserve and then with A reserve response lost. | B waits, both successful commits serialize n then higher ID. A rollback/unknown allocation burns n with zero local partial effects. B higher. Assert independent high-water, receipts, history and delivery count. |
| A commits then HTTP response is lost. Restart A, retry on B. Change only grants before retry or between known commit and response release. | Same authorized original result and ID, no second effect. Revoked actor gets concealed/masked outcome while committed facts stay. Query row counts. |
| Fault JDBC commit before forwarding on one run; forward to real DB, throw lost-ack exception after known DB commit on another. Hide writer proof during initial resolution. Retry same key after confirmed disposition. | Initial OUTCOME_UNKNOWN if proof unavailable, never re-execute on uncertain absence. Confirmed rollback allows one new effect. Commit variant resolves original result without repeating. Use DB observer for ground truth, not application mocks. |
| Alter assignment/evidence independently without changing request revision. Revoke before effect gate. Expire/purge key and restore older database image with older observation/key plus independent high-water. | Bound fact change makes token stale. Earlier revocation gives zero unauthorized effect. No new effect with expired/fenced key. Divergent equal revision rejects old token. Known safe receipt may replay. Lost IDs cannot recur. |

In each test observe status and safe code, masks, ref/revision/ID if authorized, before/after request/history/reason/receipt/outbox counts and effects, plus measured waits and cleanup. Include races through normal public routes where relevant. Exhaustion and rollback tests inject deterministic authority counters and deadlines. Loss branches require real cross-instance retained database outcomes. A production engine must pass equivalent races, commit/durability and recovery evidence, plus scoped browse and protected release ordering. Do not infer production readiness from engine candidate tests. [Acceptance](acceptance.md) · [Recovery scenario](recovery.md)
