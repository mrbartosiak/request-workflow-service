## Ordering of grant changes and release

**Proposed** Each organization has a `scope_gate` row. Take a shared lock for normal application reads and writes and exclusive lock from the start for changes to authority inputs, scope/assignment, retention/redaction or other security-visible conditions. Treat any state change that affects access/masks as exclusive. Type policy includes the declarations that determine gate mode. All grant-affecting transactions and reads, even admin updates, use this gate. Local revocation is effective at the committed exclusive update. Earlier revocation prevents a later effect or release. Normal writes also lock the request/facts. Independent authority with unproven freshness fails closed. [Transactions](transactions.md)

The post-commit response path opens a fresh, bounded authority transaction and reauthorizes target, operation, required context and output fields. For protected reads, coherent data selection and final check share a gate-held transaction. Select detail/context facts and revision in one authoritative statement snapshot, or protect them with request/fact locks through selection. Final release is the enqueue of already serialized, bounded bytes into the response delivery path while applicable shared locks still hold. At enqueue recheck any time-dependent freshness and a live reader-generation proof. Do not hold a policy lock across network transmission or client backpressure. Bytes enqueued before revocation can arrive later. A grant change between effect commit and release can conceal the result without rolling back the effect. A lost authority proof returns a safe response. [Browse](browse-history.md) · [REST](rest.md)

Use the [retry decision order](retries.md) before key disclosure. For authorized submitted intent, KEY_EXPIRED and KEY_FENCED reveal only authenticated key restrictions. An old inaccessible binding uses the same fence response as an absent one. Replay or prior-binding conflict requires current original action/target/result access and submitted access. Replay checks ownership, retention and any originator restriction without attempting the old action again. Restore requires proved current scope authority for every protected surface. [Authority continuity](authority-recovery.md)

**Alternative** Versioned directory mirror with per-scope verified watermark, freshness and fail-closed outage. It can reduce local administration but bounded lag cannot prove immediate external revocation. Adopt only after proving ordering or owner approval of a defined effective-point/freshness model. Pending proof, the local authority model is the evidence fixture.
