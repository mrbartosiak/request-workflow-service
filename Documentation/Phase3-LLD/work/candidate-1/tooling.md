# Tooling evaluation

**Scope** Owner LLD options A/B/C/D/F/H, A-02/03, Q-04/07/08, DEC-06/08/10/14. All choices are proposals. Establish pinned tools and prove Java 25/Spring 7.0.11 compatibility before adoption. Keep generated artifacts in build output and authority in the named inputs. [Owner assumptions](../../../output/Assumptions-initial-HumanMade.txt)

| Option | Source, proposed check and comparison | Adoption evidence and recommendation |
| --- | --- | --- |
| YAML/OpenAPI DTO generation | Versioned OpenAPI YAML owns public shape. Spring MVC controllers and validation own behavior. OpenAPI Generator’s Spring generator targets a Spring Boot server layout. Models-only generation might reduce duplicated DTOs, but verify JSON module, annotations, templates and runtime assumptions. Manual Java records and Spring contract tests are simpler with few routes, and require spec/DTO drift checks. | **Defer generation.** CI validates the spec and exercises JSON against approved examples. Before adoption show reproducible models-only output compiling on pinned stack with null/omitted distinctions, strict text, masks and decimal-string IDs. [OpenAPI spec](https://spec.openapis.org/oas/v3.1.2.html) · [Generator](https://openapi-generator.tech/docs/generators/spring/) |
| Compile-time DTO mapping | Java boundary DTO and explicit permitted projection types are authoritative. MapStruct uses annotation processing and configurable unmapped-field policies. It reduces mechanical mapping and adds processor setup, generated diff and compiler compatibility. Manual constructors keep tiny maps and required masks reviewable. | **Defer.** CI compiles and tests handwritten maps. Reconsider after repetitive DTO growth. Prove pinned Java 25 processor, error on missing output, sensitive projection exclusion and supported nulls. Keep permission policy explicit. [MapStruct guide](https://mapstruct.org/documentation/stable/reference/html/) |
| CI breaking API checks | Compare PR OpenAPI YAML to the last released baseline, including responses, request fields and formats. Propose pinned oasdiff CLI in CI. A checklist plus Spring MockMvc detects observed differences but requires broader human review. Spec diff misses semantics, authorization and runtime drift. | **Recommend trial.** Prove fixture that deleting an operation and changing ID string to number block, additive optional fields behave as intended, and authorized projection tests remain required. Pin CLI, baseline and exception procedure. [oasdiff](https://github.com/oasdiff/oasdiff) |
| Database-schema-derived types | Selected engine migrations are authoritative. jOOQ can generate Java schema representations. Generate against a disposable migrated database before compile in CI, avoiding shared schema introspection. Cost includes dialect, licence/edition, generator and database reproducibility. Spring JDBC explicit row maps plus engine tests provide a smaller initial stack. | **Defer.** Prove selected engine/licence, Java 25 and type fidelity for decimal-string boundary, uniqueness and secure payloads on both fresh/upgrade migration. Generated types do not prove transaction behavior. [jOOQ generator](https://www.jooq.org/doc/latest/manual/code-generation/) |
| Schema-derived event payloads | Versioned event schema plus version registry is authoritative if consumers and transport are selected. Avro defines schema resolution and Java generated records. It introduces codec/build and compatibility tooling. Initially use explicit versioned internal obligation DTOs and Spring/JDK serialization tests with fixture schemas. | **Defer generation.** CI checks old/new payloads and strict field allowlists. Reconsider when multiple external consumers need compatibility. Prove replay of retained old records, supported reader/writer evolution and Java 25 build reproducibility. [Avro resolution](https://avro.apache.org/docs/1.12.0/specification/) · [Avro Java](https://avro.apache.org/docs/1.12.0/getting-started-java/) |
| Package-boundary tests | Approved module graph and permitted packages are authoritative. ArchUnit tests bytecode package dependencies and cycles. Build module dependencies and a JDK dependency scan avoid a test library and require manual assertion tooling. Neither proves behavior or reflection wiring. | **Recommend test-only trial.** At CI compile/test prove disallowed domain→Spring, cross-adapter and cyclic references fail, allowed paths pass, and Java 25 class files are supported. Include application bootstrap and lifecycle conformance. [ArchUnit guide](https://www.archunit.org/userguide/html/000_Index.html) |

Recommend deciding tools independently. Record tested versions, generated output diff, build time, dependency/advisory review and each gate's accepted exceptions. Production engine and live schema selection remain open. [Retry evidence](postgres-evidence.md) · [Module contracts](wiring.md)
