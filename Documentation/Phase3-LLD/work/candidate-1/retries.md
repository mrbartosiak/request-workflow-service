# Operation keys, retries and retention

**Scope** A-04, F-01/05/08/09, Q-02/03/13, R-01/08/10, DEC-04/05/08. Durable scoped replay, current disclosure, no repeat effects after expiry and bounded waits are approved. Formats, budgets and precise failure handling are proposed. [HLD](../../../Phase2-HLD/retries-and-failure-timing.md)

`OperationKeyIssuer` returns a signed opaque key carrying random token ID, issuer, organization, stable principal, issued time, absolute expiry and active command generation. Scope survives role changes and applies across routes. Compare only after signature, claims and trusted-clock proof. Propose 24 hours with 3 seconds of effect-admission margin and deny new execution if authority or clock health is unproven. `IntentDigest` uses a versioned keyed digest over a length-delimited typed tuple of action, target (or Create type), original exact decoded inputs and the exact original observation token. Use purpose-specific keys and preserve derivation versions until supported comparisons expire. Replay means equality of this tuple, independent of JSON member order or transport metadata.

Authenticate, validate and check submitted target/action access before arbitration. Check key signature, scope and expiry before receipt lookup. An active key attempts unique receipt-row insertion. PostgreSQL uses `INSERT ... ON CONFLICT DO NOTHING`. If no row was inserted, read the receipt in a fresh statement after the wait. Commit the tentative receipt with effects or roll it back. Past-generation unexpired keys allow authoritative lookup only. At release, recheck submitted and original target/action access before an original success or conflict. A concealed original uses ordinary 404 for active keys. Use the uniform prior-generation outcome below for old keys. [Database insert](https://www.postgresql.org/docs/18/sql-insert.html) · [Authorization](access.md)

| Condition after access checks | Client result and durable effect |
| --- | --- |
| Active key and no retained row after authoritative arbitration | New action. Check observation and workflow. Commit once or remove the tentative row by rollback. |
| Matching successful receipt within lifetime | Original status and facts under current disclosure, including original permitted Publish ID. Never recheck historical eligibility against current state. |
| Retained receipt and changed intent | 409 `key_conflict` when both sides are currently disclosable. Zero effects. |
| Verified expired key | 409 `key_expired` uniformly from the signed cutoff after submitted-intent access. Do not look up a receipt. Zero effects. |
| Earlier generation, receipt missing, untrusted or concealed | For the same disclosable submitted intent, always 409 `retry_fenced` with the same problem fields and header policy, including no Location, replay marker or prior details. Correlation is unrelated to receipt presence. No writes. An eligible matching receipt or a fully authorized conflict still uses its ordinary outcome. |
| Wait budget exceeded or uncertain commit | 503 `outcome_unknown`. No claim about prior commit. Retry same original intent/key with jitter. |
| Proven pre-commit rollback | No success receipt. Same key may proceed within the active window after fresh checks. |

Never repeat inside an unresolved commit or failover. On the same certified primary, unique-key arbitration settles whether the old transaction committed, rolled back or still holds the key. After failover require authoritative history proof and the generation decision in [recovery](recovery.md). A timeout during commit triggers the same client result even if server-side commit later succeeds. Propose total service budget 2.4 s from admission, including pool ≤100 ms, lock wait ≤200 ms per claim with cumulative budget 400 ms, identifier authority ≤150 ms per call, capped statements and response margin. Do not restart the budget. Automatic retry at most once for proven pre-commit transient rollback with adequate remaining budget and unchanged input. After expiry resolve manually through authorized reads/support.

**Receipt retention proposals.** Signed expiry costs a preflight call and bounds replay. Client keys with compact retired markers save that call and require indefinite markers or proven safe closure. Recommend signed expiry. Purge eligible receipts 24 h after expiry, using trusted time, then enforce signed expiry alone. Retain trusted validation keys or retired epoch cutoffs. See the independent [body and reason policies](retention.md) and [restore controls](recovery.md).
