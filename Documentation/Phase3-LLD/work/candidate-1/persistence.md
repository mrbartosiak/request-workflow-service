# Records, transactions and database guarantees

**Scope** A-04, F-01–09, Q-02–04/11–13, R-01/02/08/09, DEC-03/04/05/08/11/13. Business effects are required. Record layout, locking and Java port names are proposed. PostgreSQL is a retry-evidence candidate. [HLD](../../../Phase2-HLD/local-consistency.md)

| Record | Identity and integrity |
| --- | --- |
| `Request` | PK `ref` globally unique. Immutable organization, type, originating person, name and creation tuple. Check positive `revision` and `lastSequence`. Check publication pair present exactly in PUBLISHED. Unique `(namespace,publicationId)`, signed positive 64-bit. |
| `RequestBody` | PK/FK `ref`, protected current body and retention status. |
| `TransitionFact` | PK `(ref,sequence)`, contiguous positive indexes per request. Unique `(ref,revision)`. Append-only from/to, action, recorded instant, actor reference. |
| `TransitionReason` | PK/FK `(ref,sequence)`. Protected payload present at Delete/Reject commit, separately redacted. |
| `OperationReceipt` | Unique `(issuer,organization,principal,tokenId)` across all routes. Intent digest, result action/state/ref/revision, optional ID, original HTTP status, key generation and expiry. Protected control data, no command text. |
| `PolicyGuard`, `Assignment`, `DecisionEvidence` | Guard PK organization with policy version. Scope-bound grant/mapping rows, assignment and evidence rows with independent versions. |
| `Outbox`, `Inbox`, `ExternalMapping` | Unique identities and integrity per [delivery](integration.md) and [identifiers](identifiers.md). |

Initial `revision=1`, `lastSequence=1`. Every successful existing write increments revision using checked arithmetic. Increment sequence only for state changes. Validate request state equals history tail at verification and recovery. Encode strings with byte-preserving UTF-8. Represent internal counters as bounded integer types with no overflow wrap. Enforce scoped references and uniqueness in the database. Cross-record invariants requiring joint state use exclusive command paths, transactions, constraints where supported, and integrity audits.

`TransactionRunner` owns one command transaction. After validation and preliminary access, lock the key, then exclusive organization `PolicyGuard`, then any request row. Publish takes the namespace gate last. Evaluate access and scope, signed observation, lifecycle and type policy under locks. Visibility writes including purge and admin changes take that guard exclusively. Protected release holds it shared through handoff. Lock peers in stable identity order. Commit state/body/revision, Create requester binding, applicable history/reason, receipt, approved decisions and `OutboxAppendPort` writes together. Edits add no history. Publication and ID become visible together. Rollback removes all business effects, including obligations, while burned identifiers stay consumed. [Wiring](wiring.md) · [Replay](retries.md)

**Proposed PostgreSQL proof.** Use `READ COMMITTED`, unique key insertion and guard `FOR SHARE`/`FOR UPDATE`. Read the authorized representation in fresh statements after acquiring the shared guard. Hold guards through commit/rollback or protected handoff. Bound wait and statement time. Resolve on the certified primary. Conflicting same-revision mutations allow one commit, with stale observation for a permitted loser. The organization gate serializes mutations in that organization, so measure its cost. [PostgreSQL isolation](https://www.postgresql.org/docs/18/transaction-iso.html) · [Row locks](https://www.postgresql.org/docs/18/explicit-locking.html)

**Alternative** Conditional writes match `(ref,revision,state)` in the update and validate related policy/evidence versions under a guard or serializable equivalent. Preserve incompatible ordering with disclosure through handoff. This reduces some explicit holds, while failures require careful status and full rollback. Explicit locks make authorization ordering and cross-record effects easier to inspect, while introducing waits and deadlock risk. Event sourcing would add projection, restore and compatibility obligations. Recommend transactional state and ordered history. A production engine must pass the same observed API, atomicity, ordering, uniqueness, exact-text, durability, authorization, replay and restore checks.
